STAR — AWS S3 ↔ Databricks Unity Catalog Integration

S — Situation

For the Clinical Trial Intelligence Platform, raw clinical-trial data is stored in Amazon S3, while Databricks is being used for data engineering, transformation, and analytics.

The requirement was to allow Databricks to access S3 securely without hardcoding AWS access keys or secret keys.

The architecture being established is:

Clinical Trial Data
        ↓
      AWS S3
        ↓
AWS IAM Role
        ↓
Databricks Storage Credential
        ↓
Unity Catalog External Location
        ↓
Databricks Processing
        ↓
Bronze → Silver → Gold

Unity Catalog uses a storage credential to represent the authentication mechanism for cloud storage, and an external location combines that credential with an S3 path.  

T — Task

Configure secure, least-privilege, role-based access between:

Databricks
    ↕
AWS IAM
    ↕
Amazon S3

for the project bucket:

s3://clinical-trial-intelligence-platform-sk/

without storing permanent AWS credentials inside notebooks or application code.

The integration also needed to support read and write operations, because Databricks will eventually process data and persist transformed datasets.

A — Action

First, an AWS IAM role was created specifically for Databricks:

databricks-clinical-trial-s3-role

A custom trust relationship was configured allowing the Databricks Unity Catalog AWS principal to call:

sts:AssumeRole

A temporary External ID of:

0000

was initially used because the actual Unity Catalog External ID does not exist until the Databricks storage credential has been created. This two-stage procedure is the workflow documented by Databricks.  

Next, an inline IAM policy was created:

databricks-clinical-trial-s3-policy

The policy grants the required S3 permissions for the project bucket, including appropriate List, Read and Write operations.

The role therefore separates two concerns:

Trust Policy
     ↓
WHO can assume the role?
Permission Policy
     ↓
WHAT can the role do?

This distinction is important in AWS IAM.

The IAM role ARN was then registered in Databricks as a Unity Catalog Storage Credential:

clinical_trial_s3_credential

using:

arn:aws:iam::626495478872:role/databricks-clinical-trial-s3-role

Databricks generated a unique External ID, which was then used in the AWS IAM trust relationship instead of the temporary 0000.

The External ID provides protection against the AWS confused deputy problem by ensuring the role assumption corresponds to the intended Unity Catalog credential.  

Finally, the storage credential was validated from Databricks.

Important interview learning from this step

The strongest thing to remember isn’t the console clicks. It’s this:

IAM Permission Policy = what the role can access.
IAM Trust Policy = who can assume the role.

And in your particular architecture:

S3 Policy
   ↓
"What can Databricks do?"
List/Get/Put S3 objects
Trust Policy
   ↓
"Who can become this role?"
Databricks Unity Catalog + role itself
External ID
   ↓
"Is this the intended Databricks credential?"

That is a much stronger explanation in a Data Engineer interview than saying, “I connected Databricks with S3.”

Both dry runs failed with the same RuntimeError. The root cause: during parallel analysis, Lakeflow clones the Spark session per-flow and expects the callable to use that cloned session. SparkSession.getActiveSession() returns the original module-level session, not the per-flow clone, because Lakeflow doesn't set the thread-local active session for snapshot source callables the way it does for decorated flow functions.

The fix is to declare spark_session as an optional second parameter on next_subject_snapshot. When Lakeflow detects a second parameter on the callable, it passes the per-flow cloned session explicitly through it.
