Clinical Trial Intelligence Platform

1. Project Overview

The Clinical Trial Intelligence Platform is a cloud-based data engineering and analytics project designed to integrate heterogeneous clinical-trial data originating from multiple operational systems.

Clinical-trial information is rarely generated by a single source. Subject enrollment, study operations, laboratory results, adverse events, product information, site information, and controlled vocabularies may originate from different systems and follow different structures and conventions.

The purpose of this project is therefore not merely to move data from Amazon S3 into Databricks. It is to build a governed analytical foundation through which heterogeneous clinical-trial data can eventually be reconciled and used for cross-system analysis.

The platform follows a Medallion-style architecture:

5. Why Multiple Source Domains?

Clinical trials involve multiple operational domains.

EDC — Electronic Data Capture

EDC contains subject-level clinical information such as:

* subject identifiers
* study/site association
* screening and enrollment dates
* subject status
* demographic attributes
* treatment-arm information
* clinical observations

CTMS — Clinical Trial Management System

CTMS represents operational study management, including:

* studies
* participating sites
* enrollment targets
* site activity
* operational status

Laboratory Data

Laboratory feeds contain measurements collected during subject visits.

These feeds create an important harmonisation problem because equivalent measurements may arrive with different test names, units, and representations.

Safety Data

Safety feeds contain adverse-event information used for safety surveillance and downstream analysis.

Master Data

Master datasets provide relatively stable business entities such as:

* sponsors
* products
* institutions

Protocol / Study Arms

protocol_study_arms is treated separately from generic reference data.

Study arms connect a study to its treatment/product configuration and may contain attributes such as allocation or dosage information.

This relationship is important for eventual arm-level clinical and safety analysis, rather than limiting analysis to study-level aggregation.

6. Bronze Layer Objective

The Bronze layer provides the first governed representation of the source data.

Its primary design principle is:

Preserve source-system fidelity and ingestion lineage before applying business transformations.

Bronze is therefore not responsible for full business harmonisation.

It provides:

* source-aligned records
* Delta-backed tables
* Unity Catalog registration
* ingestion metadata
* source-file traceability
* separation between operational domains
* controlled ingestion of reference/master datasets

Business standardisation, cross-system reconciliation, DQ enforcement, and quarantine logic belong primarily to Silver.

8. Why Reference Data Is Present in Bronze

Reference datasets are intentionally ingested before Silver rather than being embedded directly into transformation code.

For example:

Raw source value
      │
      ▼
Bronze operational record
      │
      ├───────────────┐
      │               │
      ▼               ▼
Raw value      Bronze reference table
      │               │
      └────── JOIN ───┘
              │
              ▼
      Standardised Silver value

This provides several advantages.

Configuration-driven harmonisation

Mappings can be maintained as data rather than being scattered through hard-coded CASE WHEN logic.

Auditability

A transformation can be traced to the reference dataset used to produce it.

Maintainability

Vocabulary changes can be managed by updating controlled mappings rather than rewriting transformation logic.

Data-quality detection

If a source value cannot be mapped against the required controlled vocabulary, Silver can identify and quarantine that record instead of silently accepting an unknown representation.

11. Streaming vs Materialized Ingestion

Not every source should be treated as though it has the same arrival pattern.

The project distinguishes between operational feeds and relatively static lookup/master data.

Operational feeds

Operational datasets may receive new records or files over time.

Examples include:

edc_subjects
edc_visits
lab_results
safety_adverse_events

Incremental/streaming ingestion patterns are appropriate where the source arrival semantics require them.

Reference and master data

Reference mappings change much less frequently and are small compared with operational clinical feeds.

For these datasets, materialized ingestion is appropriate where full recomputation is inexpensive and semantically clearer.

Conceptually:

                 BRONZE
Operational feeds              Reference/master
       │                              │
       ▼                              ▼
Incremental / streaming       Batch/materialized
where appropriate             where appropriate
       │                              │
       └──────────────┬───────────────┘
                      ▼
                    SILVER

The design choice is therefore based on data semantics, not simply on whether the source happens to be stored as CSV.

12. Bronze Lineage Metadata

Bronze ingestion retains source-file metadata where applicable.

Important metadata fields include:

_source_file
_source_file_name
_source_file_modification_ts
_ingestion_ts
_ingestion_date

For example:

.selectExpr(
    "*",
    "_metadata.file_path AS _source_file",
    "_metadata.file_name AS _source_file_name",
    "_metadata.file_modification_time AS _source_file_modification_ts"
)

and:

.withColumn("_ingestion_ts", current_timestamp())
.withColumn("_ingestion_date", current_date())

This allows a downstream record to be traced back toward the file from which it was ingested.

14. Unity Catalog Storage Architecture

The Bronze schema is associated with the S3 managed-storage root:

Unity Catalog controls the physical storage layout beneath this managed location.

The resulting physical structure may contain internally generated paths such as:

UnityManaged/
└── bronze/

        └── schemas/
            └── <schema-uuid>/
                └── tables/
                    ├── <table-uuid>/

The UUID-based directories are Databricks/Unity Catalog implementation details.

Application code should therefore address tables through logical identifiers such as:

clinical_trial_intelligence.bronze.edc_subjects

16. Dataset Snapshot Policy

The current synthetic dataset is treated as a fixed project snapshot.

It should not be regenerated casually after incremental ingestion has begun.

This matters because file-based incremental ingestion systems may track files using their paths and ingestion state.

Reusing an already-processed filename with different content can create ambiguous or misleading ingestion behaviour.

Therefore:

Once a dataset generation has been ingested and used for validation, that generation is pinned for the corresponding experiment/project milestone.

A future regenerated dataset should use a new version, date, or source prefix.

For example:

Landing_v1/
Landing_v2/

or:

Landing/EDC/subjects/load_date=2026-09-09/

depending on the eventual ingestion design.

17. File Idempotency vs Business Deduplication

These concepts are intentionally kept separate.

File-ingestion idempotency

Answers:

Have I already processed this source file?

This prevents the same physical source object from being repeatedly ingested unintentionally.

Business-record deduplication

Answers:

Do multiple records represent the same logical clinical entity or event?

For example:

subject_id = SUB-1001

may appear in multiple source deliveries because the subject record was corrected or updated.

The files may be different while the business entity is the same.

Therefore:

File deduplication
        ≠
Business-record deduplication

Both concerns must be handled independently.

18. Why Bronze Does Not Perform Full Harmonisation

Consider a laboratory feed containing inconsistent units.

An incorrect Bronze design would immediately rewrite source values:

Source
mg/dL
  ↓
Bronze

This loses the clean distinction between what arrived and what the platform derived.

The project instead follows:

Source value
     ↓
Bronze
source-preserved representation
     ↓
Silver
validated + mapped + standardised representation

This makes transformations easier to explain and debug.

20. Reference-Join Failure Principle

A particularly important Silver design consideration is reference-table availability.

Suppose a lab transformation performs:

lab_results
     │
     JOIN
     ▼
ref_unit_mapping

If the reference dataset is empty or incomplete, the join itself may still execute successfully.

Instead:

source_unit → NULL mapping

can occur for many or all rows.

The subsequent DQ rule may then classify those rows as unmappable.

Therefore, an unexpectedly high quarantine rate for a single domain may indicate a reference-data problem, rather than corruption in the operational source feed itself.

Silver preflight validation will therefore check required reference datasets before transformations are executed.

* source lineage
* reference-driven harmonisation
